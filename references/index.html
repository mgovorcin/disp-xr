    References and practices¶

    Practices disp-xr follows, where each one comes from, and which task implements it. The PRD (specs.md) states the rules; this file holds the evidence and the detail.

    How the list was built: one reader per repository read the source, docs and examples, and a second reader re-opened every cited file and tried to refute each claim. Only confirmed or corrected practices are listed. Where the reference code has a bug or a gap, it is listed under "Do not copy".

    Adoption levels: core = disp-xr does this by default; opt-in = behind the cloud extra or a keyword; example = shown in the docs gallery only.

    Downsampling rules that came out of this reading:

    • Odd integer factors (33, 67, 333) keep cell centers on 30 m pixel centers. The demos use factor 2 only.
    • A weighted median is not composable; compute each level from 30 m. A mean is composable only with stored sum(w), and with NaNs a mean of block means is not the mean of the pixels.
    • Mask and label layers need mode or "any", not a mean.
    • Build overviews after chaining and re-referencing.

    Facts about DISP-S1 granules found during this reading (to confirm in T2.2):

    • Data layers are chunked 256 x 256 with gzip level 4 and shuffle, which the HDF parser supports.
    • One frame has about 1,000 to 1,150 chunks per layer and 14 2D layers, so about 15,000 references per granule and a few million per frame.
    • time units were per-file in the 2025 production and fixed (seconds since 2010-01-01) in the 2026 production.
    • Displacement was float32 in a 2025 production granule and float64 in a 2026 one.

    1.8 Do not copy¶

    Bugs and gaps found in the reference code:

    • bowser (ops, 0a61c6a) writes proj:/spatial: attributes only on level 0 and the root, never reads spatial:*, derived_from or transform, chooses the level by comparing the pixel size in native CRS units with Web Mercator meters (so a geographic CRS always gets the coarsest level), keeps spatial_ref as a data variable, and has no Zarr tests. disp-xr writes every level self-contained, so its stores are readable by bowser and by strict GeoZarr readers. Verified on bowser's own server: none of disp-xr's extra metadata changes what bowser reads or shows, but dataset attributes must be JSON objects, not strings (see docs/bowser.md).
    • icechunk-multiscales-demo sets overview coordinates to the first pixel of each block while its transform implies block centers, and its array shapes (ceil) disagree with its coarsening (floor) when a size is not divisible.
    • topozarr coarsens by 2 only, with unweighted reductions and boundary="trim".
    • serverless-datacube-demo commits whatever sessions came back, even after failed jobs, and uses the pre-1.0 Icechunk distributed API.
    • cloud-tensor-storage-benchmarks times Icechunk writes without the commit, leaves one backend uncompressed while others use zstd, and never checks the data it reads.
    • workshop-cng-2025-zarr and icechunk-nasa pin pre-1.0 Icechunk and VirtualiZarr 1.x APIs; one workshop cell appends the wrong variable.

    2. Zarr best practices¶

    Source: zarr.dev and the documents it links: the zarr-python user guide, the Zarr v3 specification, the ZEPs and the zarr-conventions repositories. Read on Oct 1, 2026 by one reader; these rows were not independently re-checked.

    Practice Source Task
    A chunk is the unit of reading and should be at least 1 MB uncompressed. Keep the dimension you read along whole and split the others. Float32 sizes: (300, 64, 64) is 4.9 MB, (300, 128, 128) is 19.7 MB, (1, 1024, 1024) is 4 MB performance guide T14.2
    A shard is the unit of writing and must be written whole. Use sharding when small chunks would create too many objects. A 30 m frame layer at 300 epochs is about 84 GB, so shards of a few hundred MB keep the object count in the hundreds performance guide, sharding codec T14.2
    Make one dask chunk equal one shard. The worker memory budget must hold one uncompressed shard plus its encoded copy arrays guide T14.2, T37.1
    In xarray, set encoding[var] = {chunks, shards, compressors} and rechunk to shard boundaries; never pass safe_chunks=False xarray I/O guide T14.2
    The whole-time-axis timeseries preset cannot be appended to: an append rewrites every shard. Append stores use a fixed time chunk (one ministack) and time shards that are whole multiples of it. timeseries stores are frozen snapshots Follows from the sharding and append docs T14.2, T14.2b
    Default compressor is Zstandard. Benchmark plain zstd against Blosc (zstd with shuffle) for float32 with NaN, and pick from the result (done: Blosc with bit shuffle for float layers, zstd for quality layers in time-spanning chunks) arrays guide, codecs API T37.3b
    Use only spec-defined codecs from zarr.codecs by default, so GDAL and other readers work. Lossy codecs are opt-in v3 migration T14.2
    fill_value is required in v3. NaN for float layers means all-NaN chunks (water, off-frame) are not stored. Set the nodata value of integer masks explicitly; the default is 0 data types T14.2a
    xarray keeps the CF _FillValue separate from the Zarr fill_value in v3. Round-trip tests check both, and that integer masks do not come back as float xarray I/O guide T14.2a
    Consolidated metadata is experimental in v3 and not in the spec. Write it for plain stores, re-consolidate after an append, and never require it on read consolidated metadata T14.2
    Arrays written with zarr-python directly need dimension_names, or xarray cannot open them xarray Zarr encoding T27.7
    async.concurrency defaults to 10 and multiplies with dask threads. Set it through zarr.config or environment variables per job, not in code config guide T37.3a
    Parallel writers are safe only when they write different chunks (shards, when sharded) performance guide T37.4
    FsspecStore is the documented route for object storage; the obstore-backed store is marked experimental storage guide T14.2, T37.3b
    The multiscales, spatial: and proj: conventions are at version 0.1, pilot maturity, with breaking changes expected. Arbitrary scale factors (33) are allowed. GeoZarr is a suite of these conventions, not yet a finished spec multiscales, spatial, proj, geozarr-spec T27.7
    Do not rely on variable (rectilinear) chunking; that ZEP is a draft and xarray rejects it ZEPs T14.2

    3.2 Design references¶

    Nothing from these is imported; disp-xr copies an idea.

    Project Idea copied Task
    SARXarray (1.4.0, Aug 2026) Accessor layout on an SAR stack, and multi_look by coarsen with chosen statistics T9.2, T27.1
    H3, matplotlib hexbin, PostGIS ST_HexagonGrid Hexagonal binning: a global hierarchical hexagon grid (H3), and the planar hexagon lattice that hexbin and ST_HexagonGrid build (Carr et al. 1987).     xclim (0.62.0) A plain compute function wrapped by one decorator that checks units, sets CF attributes and appends history T9.3
    xarray-regrid (0.4.2) nan_threshold semantics for the valid-fraction cutoff of a cell T27.3

    xproj, rasterix CRS-aware alignment and a raster index built from the affine transform. Too early to depend on; keep grid and CRS access behind one helper so they can be swapped in, and fail on a CRS mismatch (adjacent frames can be in different UTM zones) T9.5, T36.1
    xrft (1.0.2) Spectrum scaling and window-correction conventions. Not usable directly: it needs even spacing and no NaNs T22.1, T32.4
    xskillscore, xarray-einstats Function signature (a, b, dim, weights, skipna); used as test oracles for RMSE, MAD, skewness and kurtosis T32.1, T32.6b
    xarray-spatial (0.10.18) IDW, kriging and spline used as cross-checks for disp-xr's own estimators T19.6, T24.4
    ndpyramid Pyramid generation; disp-xr writes its own multiscales metadata T27.7

    3.3 Checked and not used¶

    • Units: pint-xarray and MetPy's unit handling conflict with the rule that units live in attributes.
    • Regridding: xESMF (ESMF dependency, lat/lon focus), pyinterp.
    • Covered already: geocube, regionmask, salem, GeoWombat, Open Data Cube core (rioxarray and flox cover the need).
    • Fitting: xarray-lmfit (per-pixel lmfit is far too slow for 70 million pixels), eofs (no rotation), X-regression (dead).
    • Catalogs: stackstac, odc-stac, intake-xarray, xstac. DISP discovery goes through CMR.
    • L1 SAR readers: xarray-sentinel, xsar, pyroSAR.
    • Superseded: kerchunk formats (VirtualiZarr recommends Icechunk).
    • After 1.0: TOAD (abrupt-shift detection on (time, y, x) cubes), a candidate when automatic break detection comes into scope.
    • Other domains: the climate, ocean, radar-meteorology, machine-learning and non-Python projects on the page.
